01Product này giải quyết việc gì?

Bạn mô tả chuyến đi bằng tiếng Việt: nơi đi/đến, ngày, số người, ngân sách, sở thích. Trợ lý tìm lựa chọn, lập lịch trình có địa điểm, tính chi phí, rồi cho bạn duyệt/chỉnh sửa. Plan mới nối vào lịch sử chat; không xóa plan trước.

Tính năng product

  • Tìm vé, hotel, địa điểm qua MCP; phân biệt nguồn thật/mock.
  • Chọn combo bay, lưu trú theo đêm; lịch trình dạng thẻ/sheet.
  • Chi phí du lịch có nhóm và dòng chi tiết, cộng bằng Python.
  • Hỏi bổ sung, selective revision và lưu sở thích.
  • Mới: prompt artifacts, trace mỗi lượt, time/token/cost và tiến độ agent.

Đừng hiểu nhầm

  • Không đặt vé/thanh toán/giữ phòng; giá chỉ là snapshot.
  • Không phải mỗi agent đều có một LLM riêng.
  • Mock chạy được không chứng minh API thật khỏe.
  • Langfuse không thay LangGraph điều phối.
  • Chưa có benchmark đủ lớn để khẳng định rẻ/nhanh/chính xác hơn.
Ngân sách du lịch (VND) là tiền vé/phòng/ăn uống. Chi phí LLM (USD) là tiền vận hành model. Hai khoản được tính và hiển thị riêng.

02Agent nào, tool nào, ai quyết định?

LangGraph giữ shared state; specialist handoff bằng Command(goto=...). Không có supervisor LLM ở trên. “Swarm” ở đây là specialist handoff có kiểm soát, không phải nhiều LLM tự do hội thoại vô hạn.

Chọn tình huống để xem queue thay đổi

Tại sao chọn các kỹ thuật này?
  • LangGraph: state rõ ràng, checkpoint/interrupt hợp việc chờ người dùng duyệt.
  • Handoff: tách trách nhiệm, thay hotel không nhất thiết tìm lại flight.
  • MCP: chuẩn hóa discovery/invocation tools; không tự bảo đảm dữ liệu đúng hoặc miễn phí.
  • Structured output: schema ép hình dạng JSON, vẫn cần validate logic/ngày/giá.
  • Python budget: phép cộng và số đêm không phụ thuộc văn bản model.
  • Local-first prompts: demo không bị buộc phải có Langfuse mới chạy được.

Provider facade có 5 thao tác: search_flights, search_hotels, search_places, get_flight_booking_options, get_hotel_detail. Remote tool names/schema được adapter khám phá; tên facade không nhất thiết là tên tool trên server.

Local server cung cấp search_flights_mock, search_hotels_mock, search_places_mock, flight_booking_options_mock, find_hotel_by_name_mock. Đây là MCP stdio tools, không phải FastAPI endpoints.

04Một request chạy từ đầu đến cuối

  1. FE gửi message: POST /api/trips/start/stream. Backend tạo thread_id, run_id và queue events.
  2. Intake + validate: model trả patch; code merge và chuẩn hóa ngày/duration. Thiếu constraint thì interrupt hỏi bổ sung.
  3. Swarm: specialist đọc TravelState, gọi tool khi cần, trả update + handoff. Revision chỉ tìm lại evidence bị stale.
  4. Planner: model viết narrative theo evidence; code gắn địa điểm và cộng budget. JSON đúng schema chưa có nghĩa đúng thực tế.
  5. Review: graph tạm dừng có chủ đích, API trả awaiting_input. Stream kết thúc; không giữ kết nối trong lúc bạn nghĩ.
  6. Resume: cùng thread nhưng run/trace mới; revision router hiểu yêu cầu mới. Langfuse gom các lượt bằng session ID = thread ID. Approve lưu sở thích.
Graph state phục vụ nghiệp vụ; telemetry events phục vụ quan sát. Thẻ tiến độ UI không phải nguồn dữ liệu để dựng itinerary.

POST /api/trips/start/streamStart với progress/result/error qua SSE.
POST /api/trips/{id}/resumeClarify, revise hoặc approve.

05Prompt là artifact có phiên bản

Nội dung prompt tách khỏi Python vào YAML để review diff, có owner/changelog, deployment label và metadata truy ngược. Ba contract hiện tại:

TênBiếnSchema / version
trip_intaketoday, current_request, user_messageTripRequestPatch · v1
revision_routercurrent_request, user_messageRevisionIntent · v1
itinerary_plannertrip_request, flight, hotel, places, current_plan, revision_instruction, duration_daysPlanNarrative · production v1, staging v2
prompts/itinerary_planner/
  v1.yaml          # Baseline: messages, variables, config, metadata
  v2.yaml          # Candidate: thêm ràng buộc giờ đến/đi và evidence
  production.txt   # 1
  staging.txt      # 2
  prod-a.txt       # 1
  prod-b.txt       # 2

Version là nội dung bất biến; label là con trỏ có thể đổi. Không sửa v1 đã publish rồi gọi đó vẫn là v1: tạo version mới, ghi changelog, test. Publish script từ chối artifact đã có nội dung khác.

Local mode

PROMPT_BACKEND=local đọc alias rồi YAML từ Git. Không cần Cloud/network. Đây là mặc định.

Langfuse mode

PROMPT_BACKEND=langfuse lấy chat prompt theo label, kiểm tra contract. Cloud lỗi/schema không khớp → fallback local cùng label, có metadata.

Các chi tiết quan trọng

  • Version namespace khác nhau: artifact local v1 có thể là remote version 8. Metadata giữ version, artifact_version, source, label.
  • Pin theo run: prompt đã resolve không đổi trong cùng lượt dù Cloud đổi label. Resume là run mới nên có thể dùng phiên bản mới.
  • Cache TTL 60s: label đổi chưa chắc được mọi process nhìn thấy ngay. Khi test deploy hãy đợi cache hoặc restart BE.
  • Compile một lượt: placeholder trong input không được diễn giải lại; không phải giải pháp chống mọi prompt injection.
  • Schema Python vẫn là contract: sửa response_schema trong YAML không tự tạo Pydantic model mới.
  • Token cap: intake/revision lấy từ prompt config. Planner còn adaptive cap theo số ngày trong draft_narrative, tối đa 5.000; generation ghi cap thực tế. Muốn đổi chính sách phải đọc cả Python.
Thêm vN.yaml → validate/diff → eval có kiểm soát → staging
→ review kết quả → production → theo dõi time/cost/error → rollback nếu cần

Rollback local: đổi production.txt về version đã tốt. Cloud: chuyển label production trong dashboard, hoặc sửa alias local rồi publish --apply --promote. Lệnh promote đồng bộ alias từ repo; review trước để không ghi đè label bạn vừa chọn trên Cloud ngoài ý muốn.

06Đánh giá prompt, không chỉ thấy “văn hay hơn”

evals/planner_case.json chứa evidence đóng băng để v1/v2 nhận cùng dữ liệu. compare_prompts mặc định chỉ diff, không gọi model. Chỉ --live mới gọi tối đa hai lần; không tìm vé/hotel thật.

python -m scripts.publish_prompts         # Validate/dry-run, chưa upload
python -m scripts.compare_prompts         # Offline diff, 0 LLM calls
# Chỉ khi chủ động chấp nhận chi phí:
python -m scripts.compare_prompts --live  # Tối đa 2 LLM calls

Bài live in kiểm tra số ngày/ngày đầu, output JSON và time/token/cost. Bạn vẫn phải chấm thủ công: tới nơi 21h có bị xếp tham quan 14h? Có bịa địa điểm ngoài evidence? Có giữ vé khi chỉ đổi hotel?

Đây là eval scaffold nhỏ, chưa chứng minh v2 tốt hơn. Chưa có auto judge, quality score gửi Langfuse, confidence interval hoặc auto-promote. V2 vẫn staging.
Sticky A/B là gì?

Bật PROMPT_AB_ENABLED=true. Hash ổn định planner-v2:user_id chọn bucket 0–99; nhỏ hơn PROMPT_AB_TREATMENT_PCT vào prod-b/v2, còn lại prod-a/v1. Chỉ áp dụng planner, cùng ID giữ cùng nhánh khi cấu hình không đổi.

UI mặc định dùng demo-user nên một UI không thể hiện đủ hai nhánh; test nhiều user_id qua Swagger. Đây là routing scaffold, chưa là kết luận thống kê. Mặc định tắt để không âm thầm đổi production.

07Observability: đo đúng trước khi tối ưu

Bốn khái niệm

Session: chuyến đi/thread qua nhiều lần sửa.
Trace: một lượt start/resume/lookup.
Span: thao tác con, ví dụ hotel_agent.
Generation: span LLM với model/prompt/usage/cost.

Tại sao không dùng counter global?

Hai user chạy cùng lúc sẽ bị trộn số call. ContextVar trỏ RunRecord riêng cho request; asyncio.to_thread kế thừa context để LLM sync vẫn ghi đúng lượt.

Session = thread_id
├─ Trace: trip.start
│  ├─ parse_request → generation: trip_intake
│  ├─ flight_agent → tool: serpapi.…
│  ├─ hotel_agent → tool: booking.…
│  ├─ place_agent → tool: serpapi.…
│  ├─ planner_agent → generation: itinerary_planner
│  └─ review [awaiting_input, không phải error]
└─ Trace: trip.revise
   ├─ revision_entry → generation: revision_router
   ├─ hotel_agent → tool: booking.…
   ├─ planner_agent → generation: itinerary_planner
   └─ review

Instrument thủ công ở request/node/LLM/tool; không bọc thêm OpenAI auto-instrumentation để tránh generation trùng hoặc gửi nội dung ngoài ý muốn. Prompt Cloud được liên kết vào generation; local có reference metadata, không giả vờ là Cloud prompt.

Số đoDiễn giải đúng
elapsed_ms / duration_msWall-clock toàn lượt/thao tác, không gồm thời gian user ngồi duyệt giữa các lượt. Không cộng mọi child span để suy ra thời gian tổng.
input / cached input / outputTừ API usage. Cached là phần nằm trong input, không cộng hai lần.
cost_usdUsage × model rate; thiếu usage/rate → null, không hiển thị là miễn phí.
llm_callsSố lần thử qua cửa LLM trong run. SDK auto-retry tắt; call lỗi vẫn tính.
mcp_tool_callsGồm mock và lookup; không bằng số external search tính phí (có counter quota riêng).
fallbacksSố event fallback, không phải số sự cố độc lập.
first_progress_msĐến progress đầu tiên, không phải time-to-first-token.

Calculator minh họa — không phải hóa đơn request thật

Công thức: ((input − cached) × giá_input + cached × giá_cached + output × giá_output) / 1.000.000. Ví dụ dùng rate gpt-5.4-mini đang cấu hình: $0,75 / $0,075 / $4,50 trên một triệu token; kiểm tra nguồn khi giá thay đổi.

Chỉ một generation minh họa. Chưa gồm SerpApi, RapidAPI, Langfuse, hosting.

Override đơn giá bằng LLM_PRICES_JSON, mỗi model có input/cached_input/output (USD/million). Length error có completion usage vẫn ghi chi phí. Timeout thiếu usage được đánh dấu incomplete. Langfuse có thể dùng model catalog riêng; đối chiếu rate khi Cloud/local khác số.

Dữ liệu nào gửi lên Cloud?

TELEMETRY_CAPTURE_CONTENT=false mặc định: tên thao tác, model, prompt version, timing, usage, cost, thread/user ID và status. Không gửi compiled messages/parsed output. Publish prompt vẫn upload template tĩnh vì đó là chức năng quản lý prompt.

Bật true sẽ gửi nội dung đầu vào (có thể gồm câu user/evidence) và output đến project Cloud. Chỉ bật khi chấp nhận việc lưu nội dung. Không gửi key trong chat/prompt/commit. User ID hiện là ID demo, không phải cơ chế xác thực.

08UI biết agent nào đang làm bằng cách nào?

SSE, không phải animation đoán. BE phát event trước/sau node/tool. ui/progress.py đọc từng dòng data:, cập nhật thẻ và nhận result cuối cùng.

data: {"type":"progress","data":{"actor":"hotel_agent","status":"running",…}}

data: {"type":"progress","data":{"actor":"hotel_agent","status":"success",…}}

data: {"type":"result","data":{"thread_id":"…","state":{…},"observability":{…}}}

Thẻ chuyển đang chờ → đang thực hiện → hoàn tất/fallback/lỗi. Agent không cần tìm lại ghi “Giữ kết quả cũ”; HITL ghi “Chờ bạn”. Summary có time/token/phí LLM/calls; expander có prompt versions và các lượt trước.

  • Heartbeat mỗi 10s không có nghĩa tool đã hoàn tất.
  • Đây là POST stream; không dùng EventSource GET mặc định.
  • HTTP 200 chỉ nghĩa stream mở; cần đọc terminal result/error. Thiếu result khi mất kết nối là lỗi rõ ràng.
  • Không stream từng token narrative; chỉ tiến độ workflow.
  • Hai graph operations cùng thread bị từ chối 409; thread khác vẫn tách telemetry.
Checkpoint và run history ở RAM: restart/reload BE có thể làm thread cũ 404. Chưa có durable jobs hay replay theo event ID. Hủy stream không bảo đảm hủy HTTP LLM sync trong worker; metrics lượt bị hủy có thể thiếu usage. Không dùng số này như sổ đối soát hóa đơn tuyệt đối.

10Đọc log, debug theo lớp

Log BE nằm ở terminal Uvicorn. Có thể lưu và theo dõi:

# Terminal chạy BE và ghi log
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 2>&1 | Tee-Object -FilePath backend.log
# Terminal khác
Get-Content .\backend.log -Tail 80 -Wait
Select-String -Path .\backend.log -Pattern "run_id_cua_ban"

Event log có run/actor/status/elapsed_ms; run_finished là summary. UI expander cho xem prompt references, thế hệ model và events. Không commit log runtime hoặc raw provider payload.

Không thấy trace Cloud

Kiểm tra LANGFUSE_ENABLED, hai key, URL region, auth check và restart BE. Chờ exporter gửi batch; shutdown flush dữ liệu. Cloud lỗi không được chặn nghiệp vụ; metrics local vẫn có.

Sửa v2 nhưng vẫn chạy v1

Resume 404 / 409

404 thường vì BE restart/reload hoặc FE trỏ sai BE/port; xác nhận đúng backend rồi tạo trip mới. 409 vì thread đang chạy hoặc không chờ input; đừng resume lặp khi request trước còn chạy.

Length limit / token usage thiếu

Structured JSON bị cắt nên parse lỗi. Xem model/prompt/cap/output tokens; Planner có fallback, không retry vô hạn. Completion usage còn nhận được vẫn ghi; timeout thiếu usage không đồng nghĩa $0.

Tiến độ chỉ hiện khi xong

Kiểm tra FE gọi /stream, proxy có buffering SSE không, content type text/event-stream. Async test trong repo xác minh progress tới trước khi graph xong, không chỉ đếm event sau kết quả.
